# V免签监控 · 架构说明

## 这个系统是什么

一套**自用的个人收款监控 + 自动发卡**系统，由两个仓库组成：

| 仓库 | 作用 | 技术栈 |
|---|---|---|
| `vmq_app`（本仓库） | Android 监控端：抓收款通知、推送、记账 | Kotlin + Compose + Room |
| `vue-faka` | 服务端：订单、库存、发卡、后台 | Vue 3 + Cloudflare Pages Functions + D1 + KV |

## 核心机制：金额即订单标识

这是整套系统的基石，**不要改动**。

个人收款码没有商户订单号，通知里只有金额。所以系统这样设计：

1. 下单时，在商品价格上叠加 **±0.50 元的随机浮动**（101 个取值），生成唯一金额
2. 页面告诉买家「请精确支付 ¥X.XX」，并提示「付错金额将导致发货失败」
3. 买家扫码付款
4. 设备端监听收款通知，抓到金额
5. 推送该金额到服务端
6. 服务端按金额查 `status='pending'` 的订单，命中则扣库存、发卡密

```
买家下单 → 订单(payPrice 唯一浮动, status=pending)
    ↓
买家扫码付 ¥X.XX
    ↓
手机收到通知 → App 抓金额 → POST /api/push
    ↓
服务端: SELECT * FROM orders WHERE payPrice=? AND status='pending'
    ↓
命中 → 锁库存 → 卡密写入订单 → status=paid → 邮件备份
```

**因此**：任何改变「金额作为订单匹配依据」这个前提的方案（例如接入易支付、改走第三方网关），都属于替换架构，不是改良。

## 数据流

```
┌──────────────┐   收款通知    ┌─────────────────┐   POST /api/push   ┌──────────────┐
│ 微信 / 支付宝 │ ───────────► │    vmq_app      │ ─────────────────► │  vue-faka    │
│              │              │  (Android)      │  type/price/sign   │ (CF Pages)   │
└──────────────┘              └─────────────────┘                    └──────────────┘
                                       │                                     │
                                  ┌────┴─────┐                        ┌──────┴──────┐
                                  │ 本地账本  │                        │   D1 数据库  │
                                  │  (Room)  │                        │ 订单/库存/日志│
                                  └──────────┘                        └─────────────┘
                                       │                                     │
                                       └──── GET /api/admin/orders ──────────┘
                                              对账：找出「已收款但未发货」
```

## 消息签名

设备端与服务端共用 HMAC-SHA256 签名，防止伪造收款通知。

**签名内容**：`HMAC-SHA256(secret, type + price)`，输出小写 hex

- 设备端：`KtorClient.hmacSha256("${type}${price}", key)`
- 服务端：`Utils.sign(type, price, secret)`

**已知局限**：签名不包含 orderId 与时间戳，理论上可重放。但服务端以 `status='pending'` 作为二次拦截，重放同一笔钱无法重复发卡。彻底修复需要把 orderId 纳入签名，属于待办项（见 `TODO.md`）。

## 两个密钥不要混用

| 服务端环境变量 | 用途 | App 设置项 |
|---|---|---|
| `APP_SECRET` | 收款推送的 HMAC 签名 | 推送密钥 |
| `ADMIN_PASSWORD` | `/api/admin/*` 接口鉴权 | 后台密码 |

它们**是两个不同的值**。旧版本 App 只有一个字段同时承担两件事，导致只要服务端把两者设成不同，就必然有一半功能失败。现在已拆分为两个独立配置项。

## 双设备（店员收款）场景

系统支持多台手机同时监听，用于主手机没电/断网时的备用。

**行为**：

- 两台都收到通知、都推送 → 先到的那台发卡成功，后到的返回 404（订单已不是 pending）
- 结果正确，不会重复发卡

**已知限制**：

- 两台手机的账本各自独立，统计会重复计算
- 若两台都推送失败，需要靠「订单页对账」发现
- 对账依赖「金额唯一」这一前提，而该前提目前**没有数据库唯一索引强约束**（见 `TODO.md`）

## 页面结构

App 底部三个页签：

```
监控    权限状态、保活状态、快捷测试、运行日志
账本    今日/本周/本月统计、待确认队列、已入账流水、手动补录
订单    服务端订单列表、疑似漏发比对、重推
```

## 关键模块

| 模块 | 文件 | 职责 |
|---|---|---|
| 通知监听 | `service/PaymentNotificationListener.kt` | 抓微信/支付宝通知，解析金额 |
| 推送 | `network/KtorClient.kt` | HMAC 签名、推送、退避重试 |
| 连接诊断 | `network/ConnDiagnostics.kt` | 分层定位「为什么推不通」 |
| 订单同步 | `network/OrderSyncApi.kt` | 拉服务端订单列表 |
| 账本 | `ledger/LedgerRepository.kt` | 记账、去重、持久化 |
| 解析规则 | `ledger/TxnParser.kt` | 从通知文本提取金额与收支方向 |
| 对账 | `ledger/Reconciler.kt` | 比对账本与订单，找出漏发 |
| 保活 | `keepalive/*` | 看门狗、开机自启、厂商引导 |

各模块的设计取舍详见 `docs/modules/` 下的分册。

## 二、未修复项（按影响排序）

### 🔴 `apiFee` 手续费配置无效

后台有配置项、前端有展示文案，但后端计算订单金额时只用 `product.price`，手续费一分钱收不到。

**待决策**：这个功能要还是不要？
- 要 → 需改计价逻辑（涉及资金链路）
- 不要 → 删掉配置项和前端文案

### 🔴 签名不绑定 orderId

签名内容为 `HMAC(type + price)`，不含订单号与时间戳，理论上可重放。

**当前已由 `status='pending'` 状态机兜住**——重放同一笔钱，订单已不是 pending，无法重复发卡。彻底修复需 App 与服务端同步改动。

### 🟡 前后端订单有效期不一致

后端锁单 8 分钟，前台展示 5 分钟（差 3 分钟宽限期）。宽限期本意是给通知延迟留余地，但前端会把「付款窗口结束」显示成「订单已关闭」。

**待决策**：宽限期保留还是取消？取决于实际通知延迟情况。

### 🟡 孤儿 locking 库存不回收

先锁库存再建订单，若建单失败，库存行永久停在 `locking`，清理逻辑找不到它。

**已评审后决定不做**：常见修法（`orderId NOT IN orders`）会误杀正在创建的订单，导致买家付款后拿不到货——用更大风险换小风险不划算。

### 🟡 schema 在请求路径里维护

`/api/admin/data` 每次请求都跑 `CREATE TABLE` + `ALTER TABLE`。浪费配额，且新站首次下单时表可能还不存在。

**建议**：改为部署期迁移脚本。

### 🟢 App 无崩溃捕获、日志不持久化

日志纯内存、上限 500 条，App 重启即丢。这是当前唯一的排障手段，出问题只能靠猜。

**建议**：参考 jian_box 的 `CrashHandler` + `CrashLogPaths`。

### 🟢 后台密码硬编码在 App 源码

`AppStore.DEFAULT_ADMIN_PASSWORD` 为预填值。仓库为私有（0 fork），风险可控，但改密码需重新构建。

## 三、本次审查中的操作失误

审查时用 `{"price":"1.00","sign":"bad"}` 打生产接口，触发了真实的签名失败告警邮件。

**正确做法**：用 `dryRun: true` 或 `price: "0.00"`，这两者不会告警。

已确认该记录是审查噪音，不是系统故障。

## 四、后续建议优先级

1. **App 崩溃捕获 + 日志持久化** —— 排障能力，价值最高
2. **`apiFee` 决策** —— 要么修好，要么删掉，别留着误导
3. **schema 迁移** —— 一次性工作，消除隐患
4. **时间对齐** —— 需先确认实际通知延迟
5. **签名绑定 orderId** —— 需两端同步改，风险较高

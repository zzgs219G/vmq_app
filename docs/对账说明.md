# 对账：找出「已收款但未发货」

对应代码：`ledger/Reconciler.kt`、`network/OrderSyncApi.kt`、`ui/OrdersScreen.kt`

## 解决什么问题

系统的正常链路是「收款通知 → 推送 → 服务端按金额匹配订单 → 发卡」。这条链路任何一环失败，买家付了钱却拿不到卡密，而**服务端那边这笔订单仍然是 `pending`**，和「买家还没扫码」的订单长得一模一样。

服务端无法区分这两种 `pending`：

```
订单 A：pending，买家还没付款        ← 不用管
订单 B：pending，买家付了但推送失败   ← 必须处理
```

**唯一能区分的信息在设备端**：账本里记着「我确实收到了这笔钱」。把两边一比对，就能找出问题单。

## 匹配规则

按**金额 + 时间窗**匹配，因为金额本身就是这套系统的订单标识。

```
匹配成功 = 订单.payPrice == 账本.amountCents
         且 账本.occurredAt 落在 [订单.createTime - 10min, 订单.expireTime + 10min]
```

时间窗取 10 分钟的依据：订单有效期 8 分钟（后端锁单），收款只可能发生在订单创建到过期之间。留出余量是为了容忍系统时钟偏差与通知延迟。

## 判定结果

比对后每条记录落入四类之一：

| 情况 | 含义 | UI 提示 |
|---|---|---|
| 金额匹配且订单已 `paid` | 正常，已发货 | 不显示 |
| 已推送成功且有 `linkedOrderId` | 正常，已闭环 | 不显示 |
| 匹配到订单但仍是 `pending` | 推送可能失败 | 「对应订单仍待付款」 |
| 匹配到订单但已 `expired` | 买家付款太晚 | 「订单已过期，需退款或人工处理」 |
| 匹配不到任何订单 | 订单创建失败或金额不符 | 「服务端查不到这个金额的订单」 |

## 参与比对的记录

排除以下几类，避免误报：

- 支出记录（只关心钱进来了）
- 已被软合并的记录（重复通知）
- 用户标记为忽略的
- 手动补录的（不来自通知，服务端不一定该有订单）

## 为什么「补单」叫「重推」

发现漏发后，UI 上的按钮是「重推」，不是「补发」。

**它的行为**：拿账本里记录的金额和来源，重新调一次 `/api/push`，由服务端按金额重新匹配订单并自行决定是否发卡。

**为什么不做成「直接发卡」**：那等于开了一个「不验资就能出卡」的入口，任何人拿到后台密码就能白拿卡密。而这套系统的核心前提是「钱到了才发卡」。

钱是既成事实，需要补的只是那次失败的推送。

## 已知局限

1. **依赖金额唯一性**。如果两笔订单金额相同（浮动只有 101 个取值，理论上会撞），比对只取第一个匹配的订单。这个前提目前没有数据库唯一索引强约束，属于 `TODO.md` 中的待办项。

2. **无法处理金额被篡改的情况**。如果买家付的金额与订单 payPrice 不一致（比如手动改了金额），服务端本来就不会发卡，对账也匹配不上，会显示为「查不到订单」。

3. **时间窗是硬编码的**。如果服务端改了订单有效期，这里需要同步调整。

## 测试覆盖

`app/src/test/java/com/xixin/vmq/ledger/ReconcilerTest.kt`，12 个用例，重点覆盖两类错误：

- **误报**：金额匹配已发货、已推送成功有订单号、支出、被合并、已忽略 → 都不该报
- **漏报**：服务端无订单、订单仍 pending、订单已过期、金额不符、超出时间窗 → 都该报

漏报意味着买家付了钱你永远不知道；误报意味着你被虚假警报淹没最后不看它。两者都会让这个功能失去意义。

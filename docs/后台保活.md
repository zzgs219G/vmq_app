# 保活

对应代码：`keepalive/`

## 为什么需要保活

本应用靠 `NotificationListenerService` 抓收款通知。进程一旦被冻结，通知照样到状态栏，但 `onNotificationPosted` 不再回调——**表现得像正常工作，实际已经漏单**。这是最危险的失效模式：无声无息。

常见冻结原因：

- 国产 ROM 的省电策略（ColorOS 有独立于电池白名单的「应用冻结 / 深度睡眠」名单）
- 用户从最近任务划掉应用
- 低内存时 LMK 回收非前台进程
- 系统重启（绑定不会自动恢复）

## 关键区别：不能用 startForegroundService

通知监听服务由系统在用户授权后绑定，**应用侧无法主动 start**。用 `startForegroundService` 只会得到 "not allowed" 或一个未被系统绑定的空壳。

唯一合法的自愈入口是 `NotificationListenerService.requestRebind(componentName)`——请求系统重新绑定。本项目所有拉起路径都走这个。

## 三个组件

### Watchdog（看门狗）

`keepalive/Watchdog.kt`

每 **9 分钟**用 `AlarmManager.setExactAndAllowWhileIdle` 唤醒，检查监听是否还活着，不在就 `requestRebind`。

**为什么用 AlarmManager 而不是 Handler / ScheduledExecutor**：Doze 模式下应用没有 CPU 时间片，后两者根本不会被调度，等于没做。只有精确闹钟能在 Doze 下把进程叫醒。

**为什么是 9 分钟**：更频繁的唤醒会被 ColorOS 判定为异常唤醒并**拦截**，反而更不可靠。

**降级处理**：Android 12+ 用户可能关掉「闹钟与提醒」，此时 `setExactAndAllowWhileIdle` 抛 `SecurityException`。代码先预检 `canScheduleExactAlarms()`，失败则降级为非精确闹钟并记日志（Doze 下可能延迟数小时）。

**闹钟链自愈**：Doze 下闹钟可能被**直接丢弃**（不是延后）。因此每次维护 tick 都核对上钟时刻，超过一个周期就补上，把闹钟链从「单发」变成「自愈」。

### BootReceiver（开机自启）

`keepalive/BootReceiver.kt`

监听 `BOOT_COMPLETED` / `LOCKED_BOOT_COMPLETED` / `QUICKBOOT_POWERON` / `MY_PACKAGE_REPLACED`，启动后 `requestRebind` 并重启闹钟链。

开机瞬间系统可能仍禁止启动服务，所以用 `scheduleSoon(delayMs = 15s)` 延迟上门钟，比立刻安排更可靠。

### KeepAliveGuide（厂商引导）

`keepalive/KeepAliveGuide.kt`

按 `Build.BRAND + MANUFACTURER` 识别 6 类 ROM，每类给出**具体到设置层级**的操作路径：

```
ColorOS：设置 → 应用 → 自启动管理
MIUI：   设置 → 应用设置 → 应用管理 → 本应用 → 自启动
...
```

统一的「请把本应用加入白名单」对用户没有帮助，必须说清在设置里的哪一层。

跳转用「候选 ComponentName 列表逐个尝试」，全部失败回落应用详情页——保证任何设备上点下去都有反馈，不会静默无响应。

## should_run 机制

所有自动拉起路径（看门狗、开机、`onTaskRemoved`）都先检查 `Watchdog.shouldRun(context)`。

用户主动停止时置为 `false`，避免出现「我都关了它怎么又自己开」。用户打开 App 时重新置为 `true`。

## 已知边界

- `requestRebind` 不是 100% 可靠。若系统判定应用「已被用户强制停止」，任何自动拉起都无效，必须用户手动打开一次 App
- 部分 ROM 的「应用冻结」不看电池白名单，只能靠 `KeepAliveGuide` 引导用户手动关闭
- 无法保证 100% 不漏单，这正是**对账功能**存在的原因：漏了就靠账本与服务端订单的比对找出来

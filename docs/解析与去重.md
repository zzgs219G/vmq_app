# 解析规则与去重

对应代码：`ledger/TxnParser.kt`

## 为什么这件事最需要小心

解析错了**不会崩溃**，只会静默算错账。用户看不到任何提示，账本就在无声中变脏。

旧实现有过一个具体错误：

```kotlin
// 只要看到"转账"两个字就当收款
if (fullText.contains("转账")) { parseAndReport("wechat", fullText) }
```

但「转账」出现在两种通知里：

```
收到转账 ¥100     ← 收入
你已转账 ¥100     ← 支出
```

结果：用户用微信付钱给朋友，App 记成收了 100 块。

## 判定优先级

**核心原则：宁可判为「未知」，也不要猜错。**

| 顺序 | 规则 | 方向 | 说明 |
|---|---|---|---|
| 1 | `你已转账 ¥N` | 支出 | 必须先判，否则会被收入规则误吃 |
| 2 | `付款成功/支付成功 ¥N`、`付款 ¥N` | 支出 | |
| 3 | `退款 ¥N` | 收入 | 钱回到手里 |
| 4 | `收款 ¥N`、`到账 ¥N`、`已收款 ¥N`、`收到转账 ¥N` | 收入 | |
| 5 | 仅能识别金额（`¥N` 或 `N元`） | **未知** | 进待确认队列，由用户点选 |

第 5 条是关键设计。旧实现用宽泛的 `¥金额` 和 `金额元` 正则直接当收入，导致微信群消息、公众号推文、账单提醒全部误判成收款。现在这类只判为「未知」，在 UI 上明确标注并让用户一键归类。

## 金额用整数分

整条链路原本是 `String → parseFloat → toFixed(2)`，全程浮点。单笔展示没问题，但账本要累加，`0.1 + 0.2 != 0.3` 这类误差会累积，表现为「明细加起来和合计对不上」。

现在账本内部统一用 `Long` 存分，只在展示时转成元。转换用字符串运算而非浮点：

```kotlin
TxnParser.toCents("28.50")  // → 2850L，不经过 Double
TxnParser.toYuan(2850L)     // → "28.50"
```

## 去重

对应代码：`ledger/TxnParser.kt` 中的 `DedupRules`

### 为什么必须去重

微信一笔收款常常产生**多条**通知：

```
通知1（微信支付服务号）：微信支付收款0.01元
通知2（微信主程序）：    已收款 ¥0.01
```

不去重就会双倍记账，而且是系统性翻倍，越用账越离谱。

### 两层去重

**第一层：硬指纹**

完全相同的通知（同一包名、标题、正文、金额、方向）视为重复投递，直接丢弃。指纹用 SHA-256。

**第二层：软合并**

上面两条通知的**文本并不相同**，硬指纹拦不住。所以再加一层：

```
同来源 + 同金额 + 同方向 + 90 秒内 → 判为同一笔
```

方向必须相同，否则 `收到 ¥100` 和 `你已转账 ¥100` 会被错误合并。

### 为什么是 90 秒

实测两条通知通常相差 1~3 秒。90 秒是留足余量的折中：

- 太短 → 漏合并，仍然双倍记账
- 太长 → 真实的两笔同额交易被误合并

**误合并比漏合并安全**，因为合并是可撤销的（原始记录保留，标记 `mergedInto`），而双倍记账会污染所有统计。

### 为什么要保留原始文本

规则一定会被修正。保留 `rawText` 后，规则迭代可以对历史数据**重新解析**，不需要用户重输一遍。

## 已知局限

- 微信群消息里出现「¥20」这类文本，会进待确认队列（判为未知方向），需要用户忽略一次
- 支付宝部分版本的到账通知文案不在上述规则内，会落到「仅识别金额」分支
- 若同一个 90 秒窗口内真的收到两笔相同金额，会被合并成一笔（可撤销）

以上都需要真机样本持续补充规则。遇到未识别的情况，日志里会记录 `⚠️ 未匹配的通知: <原文>`，把原文发出来即可针对性加规则。

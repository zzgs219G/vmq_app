# 待办事项

记录已知问题与后续计划。优先级从高到低。

## 待处理

### 真机验证解析规则

`ledger/TxnParser.kt` 的正则是按常见通知文案写的，**尚未在真机上、在具体微信/支付宝版本上验证过**。

需要做的：收几笔真实款项，看账本「待确认」里出现的原始文本能否正确解析出金额与收支方向。未匹配的会记录 `⚠️ 未匹配的通知: <原文>`，把原文发出来即可针对性补充规则。

### 密钥强度

服务端 `APP_SECRET` 目前仍是弱值。它用于收款推送的 HMAC 签名，泄露后可伪造「收到 ¥X」的推送，配合能够自行下单获知金额，理论上可以白拿卡密。

`vue-faka` 仓库已转为私有且无 fork，暴露面已缩小到「可能被爬虫抓取过」的级别。轮换方式：Cloudflare → Settings → Environment variables → 改 `APP_SECRET` → 同步改每台设备 App 设置。

**变更顺序不能错**：先在 App 里填新值，再改服务端。反过来会让所有设备立刻收到 401。

### 后台密码硬编码

`AppStore.DEFAULT_ADMIN_PASSWORD` 常量里写着预填值。`vmq_app` 是私有仓库，外界不可见，但修改密码需要改代码重新构建，无法只在设置里改。

若觉得不便，可改为不预填、纯靠设置填写。

## 后端待办

以下属于 `vue-faka` 仓库，按风险排序。目前因「不想动资金链路」而延后。

### 高风险

**并发撞金额导致发错人**
下单时「查金额是否被占用」与「插入订单」之间没有原子性，并发下两单可能拿到相同 `payPrice`，之后回调必然发错人。修法：给 `payPrice` 在 `status='pending'` 上加部分唯一索引，把撞车从「发错货」变成「创建失败」。

**订单号可枚举**
格式 `YYMMDD-HHMMSS-XXXX`，后 4 位仅 9000 种取值。配合 `/api/order/check` 无鉴权无限流，可爆破出已付订单的卡密全文。修法：改高熵随机 + 给查单接口加限流。

**孤儿库存锁永不释放**
先锁库存再建订单，若建单失败，库存行永远停在 `locking`。清理逻辑只回收「能在 pending 订单里找到」的锁，孤儿锁无人管。修法：建单失败时回滚，或增加兜底清理。

### 中风险

**回调签名不含 orderId 与时间戳**
签名内容是 `HMAC(type + price)`，理论上可重放。目前靠 `status='pending'` 二次拦截，重放同一笔无法重复发卡。彻底修复需要把 orderId 与 nonce 纳入签名，并同步改设备端。

**后台鉴权是明文密码直比**
已改为常量时间比较，但仍是明文密码、无 token 过期、无失败次数限制。

**邮件备份大概率静默失败**
发送方是 `onboarding@resend.dev`，只能发往账号所有者自己的邮箱。未验证域名时发给真实买家会被拒，而失败被 `catch` 吞掉，前端仍显示「备份已发」。

**手续费未实际收取**
`apiFee` 配置项只存在于前端文案，后端计算订单金额时只看 `product.price`，手续费一分钱收不到。

### 低风险

- 订单表结构靠每次请求 `CREATE TABLE` 维护，且只在管理员登录后创建——新站首次下单会 500
- 营收统计原从 `LIMIT 500` 窗口累加，已改为 SQL 聚合
- 前端多处 `catch(e){}` 静默吞异常，线上问题无法定位
- 前端日志纯内存、上限 500 条，App 重启即丢，排障无现场
